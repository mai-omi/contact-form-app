# UAT: ACCEPTANCE.md 受け入れ条件チェック

## これは何のためのスキルか

このプロジェクトのテスト(`./vendor/bin/sail test`)はコードレベルの正しさを確認するが、「ブラウザで実際に操作したときに、要件シート通りの文言・画面遷移になっているか」は別物。`ACCEPTANCE.md` はその橋渡し役として書かれた受け入れ条件一覧なので、実装が一区切りついたら、この一覧を1行ずつ実機で突き合わせる。これにより、テストは通っているのに実際の画面では文言がずれている、といった食い違いを提出前に見つけられる。

## 引数

- 省略: `ACCEPTANCE.md` の全章を対象にする。
- 章番号をカンマ区切りで指定(例: `4,5`): その章だけを対象にする。直近のIssueで触った範囲だけ素早く確認したいときに使う。

## 対象

$ARGUMENTS

受け入れ条件そのものではなく、それが書いてあるファイルの場所を渡されたときは、
そのファイルを開いて、書かれている受け入れ条件を読んでから始めてください。

## 手順

### 1. 環境をUATしやすい既知の状態にする

```bash
./vendor/bin/sail up -d   # 起動していなければ
./vendor/bin/sail artisan migrate:fresh --seed
```

DBを毎回シード直後の状態に揃えておくと、「何件表示されるべきか」「どのメールアドレスでログインできるか」を自分で考えずに済み、受け入れ条件の文言とそのまま突き合わせられる。すでに検証用データが入っている状態で始めると、件数系の条件(例: 一覧が7件ずつページネーションされる)の判定がぶれるので、基本は毎回リセットしてから始める。

対象章を引数で絞っている場合は、既存の `uat-shots/` 内でこれから再検証する章のプレフィックス(例 `04-*`)のファイルだけ削除してから撮り直す。絞っていない場合は `uat-shots/` の中身を一度空にしてから始める(前回の実行の古いスクリーンショットが混ざって、どちらが最新の証拠か分からなくなるのを防ぐため)。なければ作成する。

### 2. ACCEPTANCE.md を読み、対象の章を特定する

リポジトリ直下の `ACCEPTANCE.md` を読む。`## N. 見出し` で章が区切られ、各章に `- ` の箇条書きで受け入れ条件が並んでいる。引数で章番号が指定されていればその章だけ、なければ全章を検証対象のリストにする。

### 3. Playwright MCPで章ごとに実機検証する

`mcp__playwright__browser_*` ツール(`browser_navigate`, `browser_snapshot`, `browser_fill_form`, `browser_click`, `browser_take_screenshot` など)でアプリ(`http://localhost`)を実際に操作し、各行の条件が満たされているか確認する。

進め方の考え方:

- **実装済みの機能**: 条件に書かれている操作(フォーム入力・ボタン押下・リンク遷移など)をそのまま再現する。バリデーションエラーの文言は`ACCEPTANCE.md`に書かれた文言と一字一句比較する(「だいたい合っている」ではなく完全一致を確認する)。複数の必須項目を一度に空で送信するなど、1回の操作で複数行の条件を同時に満たせる場合は、スクリーンショット1枚を複数行の証拠として使い、無駄に同じ操作を繰り返さない。
- **DBへの書き込みを伴う条件**(お問い合わせ送信・ユーザー登録など): 画面上の遷移だけでなく、`./vendor/bin/sail artisan tinker --execute="..."` で実際にレコードが作成されたかもDB側から裏取りする。画面遷移だけだと見た目が正しくてもDBに保存されていない、という食い違いを見逃すため。
- **まだ実装されていないルート・機能**: 1行ごとに律儀に操作して確認する必要はない。該当URLに直接アクセスして404等になることを1枚のスクリーンショットで確認すれば、その章(またはその機能に属する複数行)まとめて「未実装」と判定してよい。未実装の判定理由には、対応するIssue番号やdocs/design配下の設計書など、裏付けが分かる情報を添える。
- **章をまたいで同じ画面状態を使える場合**(例: 確認ページの表示が複数章の条件に関わる)は、スクリーンショットを使い回してよい。

スクリーンショットは `uat-shots/` に保存し、ファイル名は `章番号-行番号-内容が分かる説明.png`(例: `01-9-invalid-email-format-error.png`)とする。複数行をまとめて証拠にする場合は `01-5to13-empty-submit-errors.png` のように範囲で表す。この命名により、あとから「ACCEPTANCE.mdの何行目の証拠か」が一目で分かる。

### 4. テストカバレッジも合わせて確認する

```bash
./vendor/bin/sail artisan test --coverage
```

`ACCEPTANCE.md` 末尾の「テストカバレッジ」章(全テスト通過・70%以上)の裏付けとして使う。

### 5. 章ごとに結果を報告する

## 報告の形式

章ごとに、次の形式でまとめる。

```
## N. 章タイトル
| 行 | 判定 | 根拠 |
|---|---|---|
| (条件の要約) | ✅満たす / ❌満たさない / 未実装 | スクリーンショットのファイル名、DB確認結果など |
```

未実装の章は、行ごとの表にせず「この章は未実装(Issue #Xが未着手のため)」のようにまとめて報告してよい(1行ずつ表にする価値がない)。

最後に、全体のまとめとして「満たす章/行」「満たさない章/行」「未実装の章/行」を箇条書きで総括する。満たさない行があれば、それが実装のバグなのか、`ACCEPTANCE.md` の文言側がそもそも実装と食い違っている(要件シートの表記ゆれなど)のかも分かる範囲で書き添える。
